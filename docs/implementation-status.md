# Implementation status

Updated: 7 October 2026. Scope: foundation, demo ledger, staff controls, account ownership, MFA, customer recovery, shared-account signing, the first admin workspace and PostgreSQL staging from [the system design](system-design.md).

## Implemented and verified

- Allowlisted browser assets in `server/index.js`; repository, source, database and document paths return 404.
- Session IDs persisted in `auth_sessions`. New login and registration tokens refer to a revocable session. Sign-out revokes the server session and clears both browser token keys on customer and admin pages. Existing tokens without a session ID require a new login.
- Default test-user creation is opt-in through `DEMO_SEED=true` in non-production. Fresh database admin bootstrap requires `ADMIN_PASSWORD`, unless explicit demo seeding is enabled. See `.env.example`.
- The old incomplete transfer handler was replaced. An explicit local demo can now transfer between two Payvexis accounts after `npm run migrate:ledger` and setting `DEMO_INTERNAL_TRANSFERS=true`; ordinary and production environments return 503 without moving funds. The dashboard labels this as a demo transfer.
- The admin delete route no longer cascade-deletes financial history. Its old direct balance edit remains disabled. The new adjustment form creates a proposal for independent review.
- Activity uses recorded transaction direction and date. Dashboard card utilization reads `cardLimit` from the API.
- Card name, holder, nickname, theme, limit and four displayed controls are validated, saved and returned by the API. Failed saves no longer display a success message.
- Admin customer and audit data are escaped before insertion into HTML.
- `npm test` exercises static-file isolation, registration/session revocation, the transfer guard, card persistence, admin money/deletion guards, staff permissions and invitations, adjustment decisions, account ownership, staff MFA, customer recovery, shared signing, admin workspace restrictions and review boundaries, and PostgreSQL schema import using temporary databases. All 34 tests pass.
- An explicit, versioned SQLite ledger migration backs up the database, imports cent-accurate opening balances once, and preserves legacy transactions as read-only history. Each journal has immutable postings; account projections reconcile to postings.
- Demo internal transfers validate a 10-digit recipient account, exact cents and a unique request key. Debit, credit, paired activity records and balance projections commit in one transaction. Duplicate requests return the same receipt. The admin Ledger tab traces posted journals.
- The local database migration was applied after a backup. Two customer balances and all nine legacy transactions were preserved. Opening entries total 1,447,500 cents; journal and balance-projection discrepancies are zero.
- A second explicit SQLite migration adds staff memberships, invitations, adjustment requests and a clearing account. It maps the existing admin to `owner`. The local database was backed up before applying it; users, transactions, journals and postings match the backup. Foreign-key and journal-balance checks report zero issues.
- Admin APIs enforce owner, finance operator, finance approver, support and auditor permissions. The admin screen loads the current permissions, shows the relevant tabs, and includes staff and adjustment queues. Owners can issue one-time, time-limited staff invitations, change roles and deactivate staff; those changes revoke active sessions.
- With `DEMO_ADMIN_ADJUSTMENTS=true` in a non-production environment, an authorized staff member can propose a credit or debit up to USD 10,000. A different authorized staff member can approve or reject it. Approval writes a balanced two-sided journal, customer activity, balance projections and an audit event in one transaction. Repeated proposal keys return the same request. Proposals alone do not change balances.
- Migration `003_identity_ownership` creates explicit customer account records and active owner memberships. It backfills existing ledger accounts, creates a membership with each new registration, and revokes existing staff sessions. Account list, detail and number APIs use the authenticated membership; demo transfers check both account owners. Joint and business requests remain individual ownership with setup pending until a verified member or organization workflow exists.
- Staff password sign-in now returns a short-lived MFA challenge, never a full staff session. First-time setup shows a manual authenticator key, verifies a six-digit time-based code, then displays eight single-use recovery codes. Later sign-ins require a fresh code or an unused recovery code. Secrets are encrypted at rest, challenges expire after ten minutes and five failed attempts, and previously used time steps are rejected. Production requires a separate `STAFF_MFA_KEY`.
- The third migration was applied to the local database after a backup. All 3 users, 9 transactions, 2 journals, 4 postings and 4 ledger accounts match the backup. Two customer accounts have active owner memberships; foreign-key, ledger-projection and journal-balance checks report zero issues.
- Migration `004_customer_identity` adds email verification history and single-use hashed action tokens. When email actions are enabled, registration sends a 24-hour verification link; signed-in customers can request another within cooldown and daily limits. Password recovery uses a 30-minute link, gives the same public response for known and unknown email addresses, and revokes existing sessions after a successful reset. Transfers require a verified email after this migration. Links use URL fragments. SMTP delivers configured messages; local development writes private messages under an ignored `dev-mailbox/` directory. Production email actions require SMTP and an HTTPS application URL.
- Migration `005_shared_accounts` adds email-bound invitations, account memberships with owner/operator/viewer roles, signing policies, transfer requests and approvals, account events, and account links on cards and activity. The joint holder or business member must have a registered, verified email and accept the invitation. Owners can invite; business owners can revoke operators/viewers. Account pages display members, pending invitations and signing work.
- For explicitly enabled demo transfers, joint and business account outflows require two distinct active, verified signers. At least one signer must be an owner. Proposals expire after one hour, reserve no funds, and post only after the second eligible signature, with idempotent ledger entries and balanced postings. Customer transfer routes enforce the persisted signing policy; the admin's old direct balance edit remains disabled. Admin adjustments remain a separate two-staff review workflow.
- The fourth and fifth migrations were applied locally after separate backups. The original columns for all 3 users, 9 transactions, 2 cards, 4 ledger accounts, 2 journals, 4 postings, 2 customer accounts and 2 memberships match the pre-004 backup. Foreign-key, journal-balance, ledger-projection and activity-link checks report zero issues.
- Migration `006_admin_workspace` adds customer notes, account debit/credit restrictions and staff investigation records. The customer detail modal now shows account memberships, recent account activity, account events, active session counts, internal notes and restriction controls. Owners can add notes, revoke a customer's active sessions and set debit/credit restrictions with a reason. New registrations receive a restriction record. The transfer and adjustment posting services check restrictions when posting, including at the final shared-transfer signature.
- The new Operations tab lists existing shared demo transfer requests and admin adjustment proposals with financial status, investigation state, filters and detail history. Authorized staff may mark an operation investigating or resolved with a note; this does not approve, reject or post it. Roles enforce read and review permissions at API level. The sixth migration was applied to the local database after a backup: all 26 pre-existing application tables and 53 rows match, and foreign-key, ledger-projection and journal-balance checks report zero issues.
- `npm run migrate:postgres` now builds a fresh PostgreSQL staging schema from a consistent SQLite backup, imports and compares every row, restores indexes and financial-history triggers, and checks the financial and ownership invariants before committing. The current schema and rows load in an in-memory PostgreSQL engine during tests. See [PostgreSQL staging import](postgres-staging.md).
- Updated `bcrypt` to 6 and applied compatible dependency fixes. After the update, `npm audit --omit=dev` reports zero production dependency advisories; all 34 tests and the CSS build pass. The older Tailwind 3 build tool still brings seven development-only audit advisories, which need a separate Tailwind 4 migration or another reviewed build-tool change.

## Still required by the design

The application still uses SQLite. An actual PostgreSQL staging run needs a provisioned PostgreSQL server and `DATABASE_URL`; neither is configured in this workspace. PostgreSQL runtime repositories, a write freeze/re-import, reconciliation on the target server, restore drill and traffic cutover remain before live payment integration. The in-memory PostgreSQL test verifies SQL compatibility but does not replace a real server test.

Email delivery needs production SMTP credentials and a verified sender. A temporary live demo may set `EMAIL_ACTIONS_ENABLED=false`, which disables verification, password recovery, and member invitations while keeping production money actions disabled. Existing customer rows have no verified email until those customers complete verification. Shared-account verification currently proves control of an email address; legal business identity, KYC, delegated mandates and configurable thresholds are not implemented. The two-signer workflow is for the local demo ledger only and does not reserve funds. Funds can become insufficient between proposal and final approval; approval then fails without posting. The Operations tab covers the two existing reviewable demo workflows only; deposit, withdrawal, external transfer, provider settlement and card review queues require their domain models and adapters. Staff MFA recovery administration, customer PINs, live payments, provider-backed cards, product modules, KYC workspaces and the rest of the expanded admin console remain. The old SQLite `users.balance` column remains a demo projection. The separate staff MFA encryption key must be retained with backups; changing it without a recovery process prevents authenticator verification.
